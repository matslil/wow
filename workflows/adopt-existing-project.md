# Adopt an Existing Project

1. Inventory source, build, tests, CI, deployment, documentation, models,
   decisions, releases, operations, support, licenses, and retirement evidence.
2. Reconstruct purpose, boundary, stakeholders, behavior, architecture,
   interfaces, versions, environments, lifecycle state, and obligations.
3. Mark every statement `explicit`, `evidenced`, `inferred`, `unknown`, or
   `conflicting`; never present inference as approval.
4. Map existing evidence to methodology outcomes. Reuse equivalent artifacts
   rather than create duplicate documentation.
5. Create a provisional project definition and tailoring record.
6. Ask only material questions that repository evidence cannot answer. Continue
   independent work while answers are pending.
7. Create a prioritized sequence of coherent adoption PRs: definition, context,
   model, traceability, risks, verification, operations, retirement, then the
   first tollgate assessment.
8. Ask the human to confirm inferred authority, intent, scope, constraints, and
   lifecycle state before declaring the adopted baseline.

Do not rewrite the whole project in one adoption PR. Keep each PR useful and
leave each commit verified.
